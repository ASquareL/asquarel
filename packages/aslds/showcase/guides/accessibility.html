Engineering Guide

Accessibility

Build inclusive, accessible and usable interfaces for every user.

Accessibility is a core engineering principle of the A Square L Design System. Every component, layout and interaction should be usable with keyboards, screen readers, assistive technologies and across devices while complying with recognized accessibility standards.

Philosophy

Accessibility by Design

Accessibility is integrated into ASLDS from the beginning of the design and engineering process. Components should be usable by everyone regardless of ability, device, browser or assistive technology.

Inclusive Design

Design experiences that work for the widest possible range of users without requiring adaptation.

Universal Access

Every interface should remain usable with keyboards, screen readers, touch devices and alternative input methods.

Consistency

Maintain predictable navigation, interaction patterns and visual hierarchy throughout every product.

Standards

WCAG Compliance

ASLDS targets conformance with WCAG 2.2 AA by promoting accessible structure, readable content, sufficient color contrast, keyboard operability and compatibility with assistive technologies.

Perceivable

Content must be presented in ways users can perceive using different senses and technologies.

Operable

Navigation and interactive controls must be fully usable with a keyboard and alternative input devices.

Understandable

Interfaces should remain clear, predictable and easy to understand for every user.

Robust

Components should remain compatible with current and future browsers, assistive technologies and devices.

Semantic HTML

Build Meaningful Document Structure

Semantic HTML provides meaningful structure for browsers, search engines and assistive technologies. Every ASLDS page should use appropriate HTML elements before relying on ARIA attributes. 

<header>
    <nav>...</nav>
</header>

<main>

    <section>

        <article>

            ...

        </article>

    </section>

</main>

<footer>
</footer>

Use Native Elements

Prefer native HTML elements such as header, main, nav, section, article and footer whenever possible.

Proper Heading Order

Maintain a logical heading hierarchy beginning with one H1 followed by sequential heading levels.

Keyboard Navigation

Every Feature Must Be Keyboard Accessible

All interactive elements must be reachable using the keyboard without requiring a pointing device.

Logical Tab Order

Users should move naturally through the interface using the Tab key.

Visible Focus

Never remove keyboard focus indicators without providing an accessible alternative.

Keyboard Shortcuts

Shortcuts should complement—not replace—standard keyboard navigation.

Focus Management

Maintain Predictable Focus

Focus should move logically during user interactions and never become trapped unintentionally. 

<button autofocus>

Open Dialog

</button>

<dialog>

...

</dialog>

Dialog Focus

When a dialog opens, keyboard focus should move into the dialog and return after it closes.

Avoid Focus Loss

Dynamic updates should never leave keyboard users without an active focus target.

Assistive Technology

Screen Reader Support

Structure, labels and landmarks should provide meaningful information for screen reader users.

Descriptive Labels

Every interactive control should have a meaningful accessible name.

Landmarks

Use header, nav, main, aside and footer landmarks consistently.

Alternative Text

Images must include accurate alternative text unless purely decorative.

Color Contrast

Ensure Readable Interfaces

Text and interactive elements must maintain sufficient contrast against their backgrounds to remain readable in various lighting conditions.

WCAG Contrast

Follow WCAG 2.2 AA minimum contrast recommendations for normal and large text.

Never Rely on Color Alone

Combine color with icons, labels or text so information is available to every user.

Typography

Accessible Reading Experience

Readable typography improves comprehension, reduces fatigue and benefits every user.

Comfortable Line Length

Avoid extremely long lines of text to improve readability.

Responsive Text

Typography should scale smoothly across desktop, tablet and mobile devices.

Clear Hierarchy

Use consistent spacing and heading levels to help users scan content efficiently.

Forms

Build Accessible Forms

Every form control should include clear labels, meaningful validation messages and keyboard accessibility to support all users. 

<label for="email">

Email Address

</label>

<input
    id="email"
    type="email"
    required
    aria-describedby="email-help"
>

<small id="email-help">

We'll never share your email.

</small>

Visible Labels

Every input must have a descriptive visible label associated with it.

Helpful Validation

Display clear validation feedback that explains how users can resolve input errors.

Accessible Instructions

Provide additional guidance using helper text linked through aria-describedby.

Buttons

Accessible Button Design

Buttons should clearly communicate their purpose, remain keyboard accessible and provide visible focus indicators. 

<button
    type="button"
    aria-label="Save Changes"
>

Save

</button>

Descriptive Actions

Button text should clearly describe the action that will occur when it is activated.

Keyboard Support

Buttons should be operable using both Enter and Space keys.

ARIA

Use ARIA Responsibly

ARIA enhances accessibility only when native HTML cannot provide the required semantics. 

<button
    aria-expanded="false"
    aria-controls="menu"
>

Menu

</button>

Native HTML First

Always prefer semantic HTML before introducing ARIA roles or attributes.

Meaningful ARIA

Use ARIA only when it adds accessibility information that native HTML cannot provide.

Motion

Respect Reduced Motion Preferences

Animations should enhance the experience without causing discomfort. Users who request reduced motion should receive a simplified experience.

Purposeful Animation

Motion should communicate state changes rather than provide visual decoration alone.

Reduced Motion

Respect the user's operating system preference for reduced motion whenever possible.

Responsive Design

Accessibility Across Devices

Accessible interfaces should remain usable regardless of screen size, orientation or input method.

Touch Targets

Interactive controls should provide sufficient size and spacing for touch interaction.

Responsive Layout

Content should reflow naturally without horizontal scrolling on supported devices.

Testing

Accessibility Testing Checklist

  • ✓ Verify keyboard navigation.
  • ✓ Test with a screen reader.
  • ✓ Confirm sufficient color contrast.
  • ✓ Check heading hierarchy.
  • ✓ Validate ARIA attributes.
  • ✓ Ensure focus remains visible.
  • ✓ Test forms and validation.
  • ✓ Review responsive behavior.
  • ✓ Test reduced motion support.

Best Practices

Accessibility Best Practices

Accessibility should be considered throughout planning, design, implementation and testing rather than treated as a final checklist.

Design for Everyone

Consider diverse abilities, devices and interaction methods from the beginning of every project.

Use Native HTML

Prefer semantic HTML elements before introducing custom solutions.

Test Regularly

Verify accessibility during development instead of waiting until deployment.

Keep Improving

Accessibility is an ongoing engineering commitment that should evolve alongside the product.

Common Mistakes

Accessibility Issues to Avoid

Missing Labels

Every interactive control should have a meaningful accessible name.

Poor Contrast

Low-contrast text reduces readability and accessibility.

Keyboard Traps

Never trap keyboard users inside a component without a clear exit.

Incorrect Heading Order

Maintain a logical document hierarchy using sequential headings.

Engineering Notes

Accessibility Engineering Guidance

Build accessible components once within ASLDS so every application benefits automatically.
Avoid overriding framework accessibility behavior unless a documented engineering requirement exists.
