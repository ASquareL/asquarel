Enterprise Engineering

Engineering Standards

One engineering standard for every application, service and platform built by A Square L Innovate.

This guide establishes the engineering principles, coding standards, architectural decisions and development workflow used throughout the entire A Square L Innovate ecosystem. These standards apply to frontend applications, backend services, shared packages, documentation and deployment infrastructure.

Philosophy

Engineering Philosophy

Every engineering decision within A Square L Innovate should prioritize maintainability, scalability, accessibility, performance, security and long-term sustainability. Software is designed to evolve without requiring major architectural rewrites.

Build Once

Develop reusable solutions that can be shared across applications rather than duplicated.

Consistency

Maintain consistent engineering standards, APIs and user experiences throughout every product.

Long-Term Thinking

Design systems and software should remain maintainable for years, not only the current release.

Architecture

Core Architecture Principles

The A Square L repository is organized into independent but connected layers. Each layer has a clearly defined responsibility, allowing applications, packages and services to evolve independently while sharing common engineering standards.

Modular Design

Separate applications, packages, backend services and documentation into isolated modules with clearly defined responsibilities.

Shared Foundations

Reuse common components, utilities and design tokens through shared packages rather than copying code.

Scalable Architecture

Every architectural decision should support future products without requiring structural changes.

Documentation First

Specifications, ADRs, RFCs and engineering standards should guide implementation rather than document it afterward.

Repository

Project Folder Structure

The A Square L Innovate repository is organized using a modular architecture that separates applications, shared packages, backend services, documentation and engineering assets.

Coding Standards

General Development Rules

Every code contribution should prioritize readability, consistency and long-term maintainability.

Readable Code

Write descriptive names, avoid unnecessary complexity and keep code self-explanatory.

Single Responsibility

Every module, component and function should have one clear purpose.

Reusable Solutions

Build reusable modules instead of copying similar logic throughout the repository.

HTML

HTML Engineering Standards 

<header>
<nav>
<main>
<section>
<article>
<aside>
<footer>

Semantic HTML

Always prefer semantic HTML5 elements before adding ARIA roles.

Accessibility

Every page should follow WCAG 2.2 guidance and maintain proper heading hierarchy.

CSS

ASL Design System Standards

The ASL Design System is the single source of truth for visual styling across the ecosystem.

Never duplicate framework components inside project-specific stylesheets. Extend existing classes instead.

Design Tokens

Always use framework variables for colors, spacing, typography and sizing.

Component API

HTML must adapt to ASLDS CSS classes. Never invent replacement class names.

JavaScript

JavaScript Engineering Standards 

// One module
// One responsibility
// Export reusable functionality
// Avoid global state

ES Modules

Use modern ES module syntax throughout the ecosystem.

Progressive Enhancement

Interfaces should remain usable before JavaScript initializes.

Naming

Naming Conventions

Files

Use lowercase file names with hyphens where appropriate.

Components

Follow the official ASLDS component naming API consistently.

Variables

Choose descriptive names that communicate intent instead of implementation details.

Organization

File Organization

Every directory within the repository has a clearly defined responsibility. Files should always be placed in the most appropriate location to maintain a clean, scalable and discoverable project structure.

Applications

Production applications belong inside the apps/ directory.

Shared Packages

Reusable libraries belong in packages/ where they can be shared across multiple applications.

Backend Services

Server-side functionality should remain inside the backend/ directory.

Components

Component Architecture

Components should remain modular, predictable and reusable across the entire A Square L ecosystem.

        ↓

Application Pages

Independent Components

Each component should solve one problem and avoid unnecessary dependencies.

Shared Foundation

Components inherit typography, spacing, colors and layout rules directly from ASLDS.

Reusability

Build Once, Reuse Everywhere

Duplicate code increases maintenance costs. Shared solutions should always be preferred over project-specific implementations.

If functionality may be reused by another application, move it into a shared package instead of copying it.

Shared Utilities

Utility functions belong inside reusable packages instead of application code.

Shared Components

Improve consistency by using the same UI components throughout the entire ecosystem.

Performance

Performance Best Practices

Optimize Assets

Compress images, minimize network requests and eliminate unused code.

Lazy Loading

Load non-critical assets only when they become necessary.

Cache Efficiently

Leverage browser caching and static asset versioning to improve loading performance.

Accessibility

Accessibility Requirements

WCAG 2.2 AA

Every application should target WCAG 2.2 AA accessibility compliance.

Keyboard Support

All interactive functionality must remain fully keyboard accessible.

Responsive Design

Responsive Engineering Standards

Mobile First

Design for smaller screens before progressively enhancing larger layouts.

Flexible Layouts

Use responsive containers, adaptive grids and scalable typography.

Security

Security Best Practices

Never expose secrets, API keys or credentials within frontend code or public repositories.

Validate Input

Treat every external input as untrusted until validated.

Least Privilege

Applications and services should receive only the permissions they require.
